## 2. Evidence Hierarchy

Use the following hierarchy when determining whether a claim is supported.

**Level 1 — Direct implementation evidence**

Actual source code, executable functions, classes, configurations, API routes, data structures, checkpoints, and execution paths.

**Level 2 — Raw experimental evidence**

Per-query predictions, evaluation traces, request-level logs, confusion matrices, raw timing records, benchmark outputs, and test results.

**Level 3 — Derived experimental evidence**

Aggregated JSON summaries, statistical calculations, plots, tables, and reports that can be independently reconstructed.

**Level 4 — Research documentation**

README files, milestone reports, design documents, experimental descriptions, and existing manuscript claims.

A higher-level claim must not contradict lower-level evidence without an explicit explanation.

An existing report or Antigravity completion message does not automatically establish that something was implemented or experimentally validated.

## 3. Evidence Classification

Classify every significant claim using exactly one of these categories:

- VERIFIED IMPLEMENTED: Supported by inspected source code.
- VERIFIED EXECUTED: Supported by an actual execution trace or test output.
- VERIFIED EXPERIMENTALLY: Supported by inspected experimental records and reproducible calculations.
- REPORTED: Present in an existing report but not independently reproduced.
- PARTIALLY VERIFIED: Some evidence exists, but an important part remains unconfirmed.
- PROPOSED: Intended architecture or future functionality without verified implementation.
- UNSUPPORTED: No sufficient evidence was found.
- CONTRADICTED: Available evidence conflicts with the claim.

Keep implementation status separate from experimental-validation status.

For example, a scheduler may be implemented but not adequately evaluated. An experiment may have been executed but may use an inadequate sample size.

These are different findings and must be reported separately.
